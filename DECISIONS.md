# Decisions

A short, dated log of choices a future maintainer or agent might otherwise undo.
Add one line per decision: `Dn (YYYY-MM-DD): decision — why.` Replace a line
when a decision changes; git keeps the history.

- D1 (2026-09-27): Follow the Lupinum OSS v2 standard (Changesets, `ci.yml`, `release.yml`, `preview.yml`, pnpm quarantine, Renovate) — every Lupinum repository shares one release, security and CI setup, and the protected `npm` environment plus trusted publishing and provenance already record what was released.
- D2 (2026-09-27): Remove the release certification machinery (release ledgers, candidate sets, artifact coordinates, runtime fingerprints, source-certification lanes, release smoke, `verify-release`, the reconcile workflow and their tests in `test/release-control`), the ASVS and SBOM generators, the upstream provenance/advisory/monitoring ledgers under `security/`, the dependency-policy and compatibility-matrix scripts, the custom package-check framework, the Vercel preview and extended-security workflows, and `MAINTAINING.md`, `RELEASING.md` and `PRODUCT.md` — they recorded process instead of guarding behavior; pnpm `minimumReleaseAge`, `pnpm audit`, Renovate, publint, attw, the packed-package smoke test and npm provenance cover what they protected.
- D3 (2026-09-27): The Nuxt module stays at the repository root and `pnpm-workspace.yaml` lists `'.'` — Changesets only versions workspace packages, and moving the module would change every import path in the repository. The Nuxt package depends on the Vue package with `workspace:*`, which `pnpm pack` publishes as the exact version, so Version packages pull requests never touch the lockfile.
- D4 (2026-09-27): Nuxt and Vue are one Changesets `fixed` group tagged `v<version>`; MCP versions independently and is tagged `mcp-v<version>` — the Nuxt module pins the exact Vue version, and these are the tags earlier releases already used. `scripts/release.mjs` publishes Vue before Nuxt.
- D5 (2026-09-27): Publish the unpublished `1.0.0-rc.0` of all three packages as the first Changesets release, in prerelease mode `rc` — `release.yml` offers every version that is not on npm. Before merging, the owner re-points npm trusted publishing for `@lupinum/better-convex-nuxt`, `-vue` and `-mcp` from the deleted `publish-prerelease.yml` to this workflow (`npm trust github <pkg> --repo lupinum-dev/better-convex --file release.yml --env npm --allow-publish`, or on npmjs.com; confirm with `npm trust list <pkg>`) — trusted publishing matches the workflow file name exactly, so without it the publish fails with E403/E404. Then merge this setup. It carries only an empty changeset (removing the dead release-fingerprint code), which bumps nothing and opens no Version packages pull request (D17), so the push to `main` (or **Actions → release → Run workflow** on `main`) offers the release at once; approve the `npm` deployment, and `1.0.0-rc.0` publishes under `next` with tags `v1.0.0-rc.0` and `mcp-v1.0.0-rc.0`. Any non-empty changeset merged before that run turns the next version into `1.0.0-rc.1`. After that, changesets produce `1.0.0-rc.N`; run `pnpm changeset pre exit` in a normal pull request to release `1.0.0`.
- D6 (2026-09-27): Keep `scripts/check-boundaries.mjs` in `pnpm lint` — it guards real import layering (server code out of browser bundles, a Node-free Convex auth component, a Nuxt-free Vue package, framework-free errors) that TypeScript does not check. `test/unit/convex-auth-boundaries.test.ts` feeds it violating edges so a broken edge builder cannot pass silently.
- D7 (2026-09-27): Replace the custom package checks with `test/packed/check-packed.mjs` (publint, attw, import every public entry from the packed tarballs, and one scan for env files, keys and test credentials) — it proves the published bytes work, which is what the old checks were for.
- D8 (2026-09-27): Keep the real-backend suites (`pnpm test:integration`), the full e2e suite and the starter and packed-consumer builds (`pnpm test:starters`) as parallel CI jobs outside `pnpm verify` — they need minutes and a local Convex backend, and they test behavior users rely on.
- D9 (2026-09-27): Pin the local Convex backend binary by SHA-256 in `test/helpers/local-backend.json` — the test harness downloads and runs it, so an unpinned download would be a real attack path.
- D10 (2026-09-27): Drop the generated API-surface page generator (`scripts/generate-api-surface.mjs`, `scripts/package-entry-manifest.mjs`) — 1,100 lines to keep one docs page in sync; the package `exports`, the type declarations and the packed smoke test are the source of truth.
- D11 (2026-09-27): The docs site and the demo keep their own lockfiles outside the workspace — Vercel builds `docs/` on its own, and the demo pins published versions like a real consumer. `pnpm verify` audits all three lockfiles.
- D12 (2026-09-27): Code scanning moves to GitHub's CodeQL default setup instead of a CodeQL workflow file — the standard allows only `ci.yml`, `release.yml` and `preview.yml`. Before merging, the owner enables default setup (Settings → Code security → CodeQL analysis → Default) and changes the `main` ruleset's required status checks from `release-gate` and `analyze` to `ci` only; neither old check exists after `codeql.yml` and the release gate are removed, so no pull request could merge otherwise.
- D13 (2026-09-27): The real-backend runners (`run-mcp-auth`, `run-mcp-conformance`, `run-oauth-*`, `run-auth-concurrency`, `run-auth-export-sentinels`, `run-auth-upgrade`) are one vitest `integration` project with a shared harness in `test/integration/harness.ts` — one runner and one backend lifecycle instead of seven hand-rolled ones. The hosted "external-disposable", release-tarball and nightly-load modes are gone because they only certified releases. Concurrency races run as concurrent in-process clients against the real backend instead of worker threads or child processes, with the same winner/loser assertions.
- D14 (2026-09-27): Two-factor sign-in is proven by `test/e2e/extended/auth-two-factor.e2e.test.ts` in `pnpm test:e2e --full`, not by a separate MFA runner — the runner only re-ran suites that already run elsewhere.
- D15 (2026-09-27): The export "sentinel" framework became `test/integration/credentials-at-rest.integration.test.ts`, a scan of a real database export for stored secrets, and the packed-tarball secret scan lives in `test/packed/check-packed.mjs` — the location registry and scanner self-tests guarded the scanner, not the product.
- D16 (2026-09-27): Tests that run against packed tarballs (`check-packed`, `check-starters`, the Vue, Nuxt and MCP consumer apps, the auth-disabled build graph) live in `test/packed/`, and the real-backend schema test lives in `test/integration/check-auth-schema.mjs` — they test behavior, so they belong with the tests; `scripts/` keeps only tooling (release, agent docs, changeset lint, boundaries, schema generator, e2e runner).
- D17 (2026-09-27): `release.yml` splits the Version packages job in two: `version-prepare` runs `changeset version` (dependency code: the Changesets CLI, changelog-github, the formatter) with a read-only token and uploads a patch; `version-pr` installs and runs nothing from the repository, rejects a patch that touches anything but `package.json` versions (plus own-package ranges), `CHANGELOG.md` files and changeset files (not `.changeset/config.json`), and pushes it and opens the pull request — dependency code must never hold a token that can push or open pull requests. A patch counts only when it changes the version of a published package, so empty changesets alone open no pull request.
- D18 (2026-09-27): The release check runs only when no Version packages pull request is open and no changeset bumps a version; a manual run follows the same rule, without the former `workflow_dispatch` override — a manual run may re-offer a rejected or failed publish of an already-versioned release, but must never pack `main` while its versions are still pending.
- D19 (2026-09-27): The `main` ruleset keeps "require conversation resolution" on and "require branches to be up to date" off — unresolved review threads are open findings, while an up-to-date requirement forces a rebase and a full `ci` rerun before every merge, and `ci` on the push to `main` already reports a broken combination.
- D20 (2026-09-27): Until 1.0.0, README files, package READMEs, `MIGRATING.md` and the docs install with the `@next` dist-tag instead of an exact `1.0.0-rc.N` — every release candidate would otherwise leave stale pins; `next` always points at the newest release candidate.
- D21 (2026-09-27): `scripts/lint-changesets.mjs` also requires a changeset that bumps a published package (at least `patch`) when its `dependencies` or `peerDependencies` change, and allows up to five lines of detail after the summary line — users install those ranges, so changing them is a user-visible change.
- D20 (2026-10-03): `pnpm-workspace.yaml` (root, `docs/`, `demo/`) ignores exactly GHSA-vfj7-8cjw-p6xm (braces) and GHSA-86w9-cpqp-85rv (node-forge) in `auditConfig.ignoreGhsas` — neither has a patched release, both arrive only through Nuxt development tooling (nitropack globbing, listhen dev certificates) and reach no published package, and failing `audit` on every pull request until upstream ships a fix would block all work. Remove each entry when a patched release passes the quarantine.
- D21 (2026-10-03): `'skip'` stops a query and clears its data, also with `keepPreviousData` — applications use `'skip'` to hide data when access ends, and `keepPreviousData` only covers new arguments that load. A component that must keep showing data during a transition freezes its view instead (#165). Keeping data across `'skip'` may come later only as an explicit opt-in option, never as a change of the default.
- D22 (2026-10-03): Queries track their arguments, and each top-level field can be a ref; `mutate()`, `run()` and `submit()` read their arguments once and pass a plain snapshot to Convex, the optimistic update and DevTools (#163, #171) — Convex runs pending optimistic updates again on new server data, so a live reactive object would show values that were never sent. Bound arguments per mutation were rejected: in three applications the repeated ID was spread across different mutations, which a scope object (`reactive({ id })` spread into each call) covers.
- D23 (2026-10-03): Packaged agent documentation (`dist/agent/`) starts with a generated entry page (task table, rules, the full index in navigation order) and uses links that resolve inside the package. Applications opt in with one pointer in their own `AGENTS.md` that the README provides; no install hook or CLI command edits project files — Better Convex is a toolkit, and the pointer names the installed package, so upgrades select matching documentation.
