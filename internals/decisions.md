Add one line per decision: `Dn (YYYY-MM-DD): decision — why.` Replace a line
when a decision changes; git keeps the history.

- D1 (2026-09-27): Follow the Lupinum OSS v2 standard (Changesets, `ci.yml`, `release.yml`, `preview.yml`, pnpm quarantine, Renovate) — every Lupinum repository shares one release, security and CI setup, and the protected `npm` environment plus trusted publishing and provenance already record what was released.

- D3 (2026-09-27): The Nuxt module stays at the repository root and `pnpm-workspace.yaml` lists `'.'` — Changesets only versions workspace packages, and moving the module would change every import path in the repository. The Nuxt package depends on the Vue package with `workspace:*`, which `pnpm pack` publishes as the exact version, so Version packages pull requests never touch the lockfile.
- D4 (2026-10-08): Nuxt and Vue are one Changesets `fixed` group — the Nuxt module pins the exact Vue version. With two fixed groups (D33), the standard `scripts/release.mjs` tags each package `<name>@<version>` and publishes a package after the packages it depends on. Releases up to 1.0.0-rc.1 used `v<version>` and `mcp-v<version>`.
- D5 (2026-09-27): Publish the unpublished `1.0.0-rc.0` of all three packages as the first Changesets release, in prerelease mode `rc` — `release.yml` offers every version that is not on npm. Before merging, the owner re-points npm trusted publishing for `@lupinum/better-convex-nuxt`, `-vue` and `-mcp` from the deleted `publish-prerelease.yml` to this workflow (`npm trust github <pkg> --repo lupinum-dev/better-convex --file release.yml --env npm --allow-publish`, or on npmjs.com; confirm with `npm trust list <pkg>`) — trusted publishing matches the workflow file name exactly, so without it the publish fails with E403/E404. Then merge this setup. It carries only an empty changeset (removing the dead release-fingerprint code), which bumps nothing and opens no Version packages pull request (D17), so the push to `main` (or **Actions → release → Run workflow** on `main`) offers the release at once; approve the `npm` deployment, and `1.0.0-rc.0` publishes under `next` with tags `v1.0.0-rc.0` and `mcp-v1.0.0-rc.0`. Any non-empty changeset merged before that run turns the next version into `1.0.0-rc.1`. After that, changesets produce `1.0.0-rc.N`; run `pnpm changeset pre exit` in a normal pull request to release `1.0.0`.

- D13 (2026-09-27): The real-backend runners (`run-mcp-auth`, `run-mcp-conformance`, `run-oauth-*`, `run-auth-concurrency`, `run-auth-export-sentinels`, `run-auth-upgrade`) are one vitest `integration` project with a shared harness in `test/integration/harness.ts` — one runner and one backend lifecycle instead of seven hand-rolled ones. The hosted "external-disposable", release-tarball and nightly-load modes are gone because they only certified releases. Concurrency races run as concurrent in-process clients against the real backend instead of worker threads or child processes, with the same winner/loser assertions.
- D14 (2026-09-27): Two-factor sign-in is proven by `test/e2e/extended/auth-two-factor.e2e.test.ts` in `pnpm test:e2e --full`, not by a separate MFA runner — the runner only re-ran suites that already run elsewhere.
- D15 (2026-09-27): The export "sentinel" framework became `test/integration/credentials-at-rest.integration.test.ts`, a scan of a real database export for stored secrets, and the packed-tarball secret scan lives in `test/packed/check-packed.mjs` — the location registry and scanner self-tests guarded the scanner, not the product.
- D16 (2026-09-27): Tests that run against packed tarballs (`check-packed`, `check-starters`, the Vue, Nuxt and MCP consumer apps, the auth-disabled build graph) live in `test/packed/`, and the real-backend schema test lives in `test/integration/check-auth-schema.mjs` — they test behavior, so they belong with the tests; `scripts/` keeps only tooling (release, agent docs, changeset lint, boundaries, schema generator, e2e runner).
- D17 (2026-09-27): `release.yml` splits the Version packages job in two: `version-prepare` runs `changeset version` (dependency code: the Changesets CLI, changelog-github, the formatter) with a read-only token and uploads a patch; `version-pr` installs and runs nothing from the repository, rejects a patch that touches anything but `package.json` versions (plus own-package ranges), `CHANGELOG.md` files and changeset files (not `.changeset/config.json`), and pushes it and opens the pull request — dependency code must never hold a token that can push or open pull requests. A patch counts only when it changes the version of a published package, so empty changesets alone open no pull request.
- D18 (2026-09-27): The release check runs only when no Version packages pull request is open and no changeset bumps a version; a manual run follows the same rule, without the former `workflow_dispatch` override — a manual run may re-offer a rejected or failed publish of an already-versioned release, but must never pack `main` while its versions are still pending.
- D19 (2026-09-27): The `main` ruleset keeps "require conversation resolution" on and "require branches to be up to date" off — unresolved review threads are open findings, while an up-to-date requirement forces a rebase and a full `ci` rerun before every merge, and `ci` on the push to `main` already reports a broken combination.
- D20 (2026-09-27): Until 1.0.0, README files, package READMEs, `MIGRATING.md` and the docs install with the `@next` dist-tag instead of an exact `1.0.0-rc.N` — every release candidate would otherwise leave stale pins; `next` always points at the newest release candidate.
- D21 (2026-09-27): `scripts/lint-changesets.mjs` also requires a changeset that bumps a published package (at least `patch`) when its `dependencies` or `peerDependencies` change, and allows up to five lines of detail after the summary line — users install those ranges, so changing them is a user-visible change.
- D28 (2026-10-03): `pnpm-workspace.yaml` (root, `docs/`, `demo/`) ignores exactly GHSA-vfj7-8cjw-p6xm (braces) and GHSA-86w9-cpqp-85rv (node-forge) in `auditConfig.ignoreGhsas` — neither has a patched release, both arrive only through Nuxt development tooling (nitropack globbing, listhen dev certificates) and reach no published package, and failing `audit` on every pull request until upstream ships a fix would block all work. Remove each entry when a patched release passes the quarantine.
- D29 (2026-10-03): `'skip'` stops a query and clears its data, also with `keepPreviousData` — applications use `'skip'` to hide data when access ends, and `keepPreviousData` only covers new arguments that load. A component that must keep showing data during a transition freezes its view instead (#165). Keeping data across `'skip'` may come later only as an explicit opt-in option, never as a change of the default.
- D22 (2026-10-03): Queries track their arguments, and each top-level field can be a ref; `mutate()`, `run()` and `submit()` read their arguments once and pass a plain snapshot to Convex, the optimistic update and DevTools (#163, #171) — Convex runs pending optimistic updates again on new server data, so a live reactive object would show values that were never sent. Bound arguments per mutation were rejected: in three applications the repeated ID was spread across different mutations, which a scope object (`reactive({ id })` spread into each call) covers.
- D23 (2026-10-03): Packaged agent documentation (`dist/agent/`) starts with a generated entry page (task table, rules, the full index in navigation order) and uses links that resolve inside the package. Applications opt in with one pointer in their own `AGENTS.md` that the README provides; no install hook or CLI command edits project files — Better Convex is a toolkit, and the pointer names the installed package, so upgrades select matching documentation.
- D24 (2026-10-03): `mutate()` and `run()` accept the same argument shape as queries: each top-level field may be a ref, and the snapshot reads refs at any depth as their current value (found by the proving app). Before, a ref inside a plain argument object reached `convexToJson` and failed with an opaque error; one rule for queries and calls is easier to learn than "refs only in queries".
- D25 (2026-10-03): Query composables have no `refresh()` — Convex keeps every subscribed query current and answers a re-read from its cache, so a manual re-run cannot return anything new; a visible no-op teaches the wrong model ("my data is stale").

- D26 (2026-10-04): The paginated query's list restart is `restart(cursor?)`, not `reset()` — every other composable's `reset()` clears local state and cancels unsent work, while this call drops loaded pages and subscribes again, so one name would mean opposite costs.

- D27 (2026-10-05): Rate-limit cleanup uses one component-owned scheduling row and the `lastRequest` index, with at most 128 deletions per mutation — the persisted row debounces bursts, and the scheduled chain expires one-time keys without changing the atomic counters. The scheduling table is outside Better Auth metadata and cannot be accessed through the adapter.

- D28 (2026-10-05): `client.connect: 'on-demand'` registers no client plugin; the browser runtime is reached only through the generated `#convex/client-activation` module, whose loader is a dynamic import of the `#convex/browser-runtime` alias behind `import.meta.client`. The server bundle drops it, and public pages never download the Convex or Better Auth client. The auth route middleware activates for pages with `convexAuth` metadata, so protected pages need no extra code.

- D29 (2026-10-05): SSR auth per route is a Nitro route rule (`convex: { ssrAuth }`) copied onto the event by a Nitro plugin, with `auth.ssr` as the build default. Nuxt's client route-rule matcher drops unknown keys, while Nitro's own matcher is the one ISR and caching already use. A route without SSR auth renders anonymously, reads no cookie, and adds no `Vary: Cookie`; the server middleware defers `convexAuth` decisions to the browser there.

- D30 (2026-10-05): Several site origins on one deployment use a signed `x-bcn-public-origin` pair (HMAC with `BCN_AUTH_PROXY_IP_SECRET`, prefix `origin-v1`, so a client-IP signature never verifies as an origin) plus the `siteOrigins` allowlist. Better Auth gets that origin as its static `baseURL` and only trusted origin per request, instead of Better Auth's `allowedHosts`, which would derive the origin from request headers. The OAuth provider and MCP keep the `SITE_URL` issuer, so `siteOrigins` is rejected with them.
- D31 (2026-10-06): `@lupinum/better-convex-functions` (`packages/functions`) is an opt-in layer, not part of the toolkit — `defineFunctions` wraps every function and holds one rule per table, which the "toolkit, not a framework" rules forbid for the Nuxt and Vue packages. An app that does not install it is unaffected, and an app that does can still write a plain Convex function behind `trusted(reason, fn)`. The three-applications rule is met by the walking skeleton's agency, content and marketplace slices, each built from a real app's feature. It depends only on `convex`, versions on its own in the `0.x` line outside the Nuxt + Vue `fixed` group, and moves to `1.0.0` together with a stable agents API. It keeps one `libraryTables` object, agent tables included, because its row rules close every library table to app handlers and its actor lookup reads the grant, run and approval rows; the agents package reuses that object.
- D32 (2026-10-07): Signing out of the web app also disconnects the person's MCP hosts and agents. An OAuth grant is bound to the Better Auth session that gave consent, and every tool call checks that session live (`requireMcpPrincipal`, the agents door through `defineFunctions`), so the next call after sign-out fails and the host must reconnect. We keep it: logout ends everything, which is the behaviour people expect from "sign out". `auth.mcpAuthorization(ctx)` is the one call that hands the MCP door this profile's resource, issuer, scopes and verifier.
- D33 (2026-10-07): Functions and Agents are a second Changesets `fixed` group, and Agents names the exact Functions version as its peer (`workspace:*`). Agents uses `./internal` of Functions, which is not under semver, so only the same version is known to work; a caret range such as `^0.1.0` would also accept a later `0.1.x` with changed internals, and outside a fixed group each `0.x` minor of Functions would leave Agents' range behind. Each package gets its own tag (D4). This replaces the "versions on its own" part of D31.
- D34 (2026-10-07): A package name that is not on npm yet cannot go out through `release.yml`. The publish job has only OIDC (`id-token: write`, no `NPM_TOKEN`), and npm trusted publishing can be set up only for a package that exists. So before the first Version packages pull request that releases `@lupinum/better-convex-functions` and `@lupinum/better-convex-agents` merges, the owner publishes each name once by hand from their own account and runs `npm trust github <pkg> --repo lupinum-dev/better-convex --file release.yml --env npm --allow-publish` for it (confirm with `npm trust list <pkg>`), as in D5. After that first release, one follow-up pull request sets the starter's `0.0.0` placeholder pins of both packages to the released version and regenerates its lockfile.
- D35 (2026-10-07): Agents are first-class actors in `@lupinum/better-convex-functions`, next to people, visitors and jobs. The functions package owns everything about who acts and with what authority, including the agent tables in `libraryTables` (grants, approvals as authority, activity, rate limits, approval parties): it resolves the actor on every call and its row rules must keep app handlers out of those tables. `@lupinum/better-convex-agents` owns the doors: tools, the approval workflow functions and the MCP door. A plugin hook that lets agents register its tables and an actor resolver was rejected: it adds a configuration step to every app and a seam in the authorization path, for purity alone. `agentRuns` and `agentMessages` belong to the in-app runtime and move with it when it becomes a package.
- D36 (2026-10-07): The MCP door keeps its live grant check, and the token endpoint keeps its own session lookup. Measured on a dev deployment: the door's `oauthLiveAccess` query came from Convex's query cache in 67 of 77 calls, so removing it would save almost nothing, while it would need a new option on the public auth API and remove a defence layer for apps that use `handleMcpRequest` with their own tools. The session refresh (`/convex/token`, 7 small calls every ~15 minutes) reads the session and user twice, once in Better Auth's middleware and once in our endpoint; merging them saves about two mostly cached calls per refresh in the most sensitive auth path. Revisit either only when measured latency or cost asks for it. A combined grant row (W6) is rejected for the same reason: it would be derived data in the authorization path.
- D37 (2026-10-08): The repository follows the current Lupinum OSS standard: the starter's `release.yml`, `preview.yml`, release, changeset-lint and dependency-audit scripts, Renovate config and templates, and the shared file layout. Kept exceptions: `.github/workflows/live.yml` stays, because the cloud smoke runs the MCP OAuth starter against a real Convex deployment, which `ci.yml` cannot (FILE-01: live.yml). `scripts/agent-docs.mjs` stays ours, because it opens each package's agent docs with a "Start here" table and the rules agents most often get wrong, where the starter's copy writes only the page index (FILE-10: agent-docs.mjs). The docs keep their sections (overview, get-started, build, recipes, concepts, operations, reference), because renaming them changes every docs URL that users and agents link to (DOC-04). The dependency quarantine also covers `@lupinum/*`, unlike the starter: a version of our own packages waits 24 hours like any other.
- D38 (2026-10-08): `@lupinum/better-convex-functions` and `@lupinum/better-convex-agents` 0.1.0-rc.0 have no provenance, because D34 has the owner publish a new package name once by hand. Their next version goes out through `release.yml` with provenance; remove this line then (NPM-02: provenance).
- D39 (2026-10-13): The auth factory never enables a sign-in method the app did not name, and never makes a Better Auth default less safe. So `emailAndPassword` is off unless passed as an object (then `requireEmailVerification` and `revokeSessionsOnPasswordReset` default to `true`); a change of password ends other sessions; verifying an address ends every earlier session of that user; a user with an unverified email is created only through password sign-up; `beforeUserCreate` may only change the id and the letter case of the email; `twoFactor` is refused together with `emailOTP` or `socialProviders`; email codes are stored hashed. Mail without an `email` hook goes to a dev outbox only when `SITE_URL` is a loopback origin (never decided by `NODE_ENV`), and a deployment with `SITE_URL` set that must send mail without the hook fails at `createBetterConvexAuth` (with `SITE_URL` unset it loads, so the first push works, and sending fails at request time). Social providers may not set `overrideUserInfoOnSignIn` (it rebinds a user to an unverified provider email and re-verifies on every sign-in). The email-code password reset routes (`/email-otp/request-password-reset`, `/email-otp/reset-password`) stay closed unless `emailAndPassword.passwordReset` is true. Known gap: the server cannot tell an owner verifying their own password sign-up from a victim opening a squatter's mail, so the squatter's password survives verification; apps that decide access by email use email codes (docs: password sign-in page).
- D40 (2026-10-13): The OAuth provider keeps `refreshTokenReuseInterval: 10` (pinned in `oauth-security.ts`, set by the MCP profile). Within the window the provider replays the same cached response (`oauth-refresh-transport.ts`), so an attacker who holds a just-rotated token gets nothing the first caller did not already get, while `0` breaks a client that retries after a lost response.
- D41 (2026-10-14): The Nuxt package supports Nuxt `^4.6.0 || ^5.0.0-0` with one code path: server code imports from `nuxt/server` and uses web `Request`/`Response`, and the `h3` dependency goes away (it stays a devDependency for tests). Temporary compatibility code for Nuxt 4 and the Nuxt 4.6 transpile regression is tracked in `internals/migrations.md`. Five choices: (1) the floor is 4.6.0, because `nuxt/server` first ships there; supporting 4.5 would need two sets of examples and a runtime that relies on Nuxt 5's temporary Nitro v2 layer. (2) The auth proxy keeps its stall guard on Node by running cleanup on the response's `close` event, because the returned `Response` ends the handler before a slow client finishes reading, and the security test for that guard stays as it is. (3) On Nuxt 5 a `routeRules` `headers` or cache rule, or a middleware, overrides the `Vary: Cookie` / `Cache-Control: private, no-store` headers on pages with SSR auth; enforcing them would need one hook per Nitro major, so the module warns at build and the docs say it. (4) No upstream issue is filed without the owner's OK. (5) The port lands as one pull request with atomic commits. The `./server` helpers (`serverConvex`, `getConvexUser`, `requireConvexUser`) read the server's runtime config, not a per-request copy, because `nuxt/server` `useRuntimeConfig()` takes no event; on Nuxt 4 with per-request env (Cloudflare module workers) the Convex config must be set at build or boot time. Nuxt 5 is called "tested on the nightly" until it is released; drop the `-0` from the range then.
- D42 (2026-10-15): Agents send files through one-time upload links, not through MCP. `request_upload` (opt-in built-in tool, scope-gated) returns tokens stored only as SHA-256 hashes; `uploadRoute` (an HTTP action the app mounts) checks the token before it reads the body, reads at most the link's size, decides the type from the first bytes and stores only an allowed type; `claimUpload` hands the file to the actor that asked for the link, once, inside a mutation operation. The actor comes from the call's `ctx.db` (`callOf`), not from `ctx.actor`, which app code can replace. Raising the 64 KiB MCP request limit or taking base64 in tool input was rejected: it removes the small-body defence of the door and still cannot carry a 10 MiB PDF. A file-argument validator was rejected for now: MCP's own file inputs (SEP-2356) and ChatGPT's `openai/fileParams` are still moving, and a claim inside the handler already covers the safety rule. People in the browser keep the recipe in `5.files/1.upload-files.md` until the Vue upload composable gets a claim option.
- D43 (2026-10-16): The auth component's rate limit (`consumeRateLimit`) is a leaky bucket: it admits a burst of `max`, and one request drains every `window / max`. Better Auth's own rule counts until a key has been idle for a full window, so steady traffic below the limit (a busy tab, several tabs behind one office IP on `/convex/token`) still reached `max` and was refused. The nominal rate per rule is unchanged, so an attacker gets no more requests than before. The browser treats a 429 from the token exchange as "wait", not as a sign-out: it asks again after Retry-After with exponential backoff and jitter while Better Auth still reports the session.
- D44 (2026-10-16): A temporary SSR token-exchange failure (429, 5xx, timeout, network) for a request that carries a session cookie is "unknown", not "signed out". The existing snapshot already publishes `authError`, so `useConvexAuth().status` is `'error'` (same wording as the browser's `AUTH_UNAVAILABLE`); no new state or type. The route middleware does not redirect while rendering on the server with status `'error'`; the page renders and the browser, which waits out temporary failures (D43), decides on hydration. Definitive answers (no cookie, 401, 403) stay `'anonymous'` and redirect as before. The browser-side decision after its own retries are exhausted is unchanged.
