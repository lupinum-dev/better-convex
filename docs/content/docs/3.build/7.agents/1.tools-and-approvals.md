`@lupinum/better-convex-agents` turns operations from
`@lupinum/better-convex-functions` into tools. A tool call runs the same
operation as the web, with the same policy and row rules, as an **agent**: the
AI host or in-app assistant that acts for one person, within the scopes that
person granted. Start with [Start here](/docs/build/functions/start-here) if
you have no operations yet.

## Give an operation a tool

Add a `tool` field to a query or mutation, as `list` and `archive` in
[Start here](/docs/build/functions/start-here) do:
`tool: { name, description, args }`.

| Field         | Rule                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------ |
| `name`        | 1 to 64 letters, digits, `_` or `-`. Unique. `check_approval` and `housekeeping` are taken |
| `description` | What the tool does, for the model. Say which other tool gives the IDs it needs             |
| `args`        | Optional text for each argument. Convex validators carry no descriptions                   |

The tool's input schema comes from the operation's validators. The tool
checks every input against the same validators, and a wrong field fails with
`INVALID_INPUT` and a message that names it.

- A query with `paginationOpts` becomes a tool with `cursor` and `limit`
  (1 to 100, 50 by default). Its `result` is `{ items, next }`; see
  [What a tool returns](#what-a-tool-returns).
- A mutation gets an optional `request_id`. A host that retries with the same
  value gets the first result back; the write runs once. A new value is a new
  call: while the same call waits for a person, it joins that request, but
  after the decision it asks again. Do not name an argument `request_id`,
  `cursor` or `limit` yourself; `defineTools` refuses it.

::warning
Change a tool only by adding to it: a new argument is optional, and an old one
keeps its meaning. Hosts keep the tool list until they reconnect. For a
breaking change, add a tool with a new name and keep the old one until no host
uses it.
::

## Collect the tools

One module calls `defineTools` with the operation modules, and exports one
internal function per tool under the tool's name. Logs and usage then name the
tool.

```ts [convex/agents.ts]
import { defineTools } from '@lupinum/better-convex-agents'

import { internal } from './_generated/api'
import { fns } from './functions'
import * as pages from './pages'
import * as projects from './projects'

export const tools = defineTools(fns, { pages, projects }, { functions: internal.agents })

export const { edit_page, list_projects, archive_project, check_approval, housekeeping } =
  tools.functions

// For the approval page: open requests, one request, and the decision.
export const { pending, get, approve, decline } = tools.approvals
// What agents did, newest first.
export const { activity } = tools
```

`functions` must be `internal.<this module>`. When `createMcpServer` loads, a
tool that is not exported fails, with the missing names in the message. An
operation in a module that you do not pass to `defineTools` has no tool.

## Hold an action for a person

Set the agent rule of the action to `'approve'` in the
[policy](/docs/build/functions/policy-and-roles). An agent that calls the tool
then gets this result instead of the effect:

```json
{
  "status": "needs_approval",
  "approvalId": "k57…",
  "summary": "Archive the project \"Website relaunch\".",
  "url": "https://app.example.com/approvals/k57…"
}
```

The agent tells the person to open the link. Your approval page at
`/approvals/[id]` reads the request with `api.agents.get` and calls
`api.agents.approve` or `api.agents.decline`. `starters/mcp-oauth-agent` has
the page in `app/pages/approvals/[id].vue`. Set `SITE_URL` on the Convex
deployment: the link is built from it.

Use `'approve'` for every action that destroys, publishes, sends, spends or
changes who has access. See [Prompt injection](/docs/build/functions/threat-model#prompt-injection).

### The plan

A person approves a plan: a fixed list, not an instruction. Give the mutation a
`plan` function, as `archive` in Start here does. It returns the sentence the
person reads and the existing rows the work will change:

```ts [convex/projects.ts]
export const archiveMatching = mutation({
  action: 'projects.archive',
  args: { orgId: v.id('orgs'), prefix: v.string() },
  returns: v.number(),
  tool: { name: 'archive_matching', description: 'Archive the projects whose name starts so.' },
  plan: async (ctx, { orgId, prefix }) => {
    const found = await matching(ctx, orgId, prefix)
    return {
      summary: `Archive ${found.length} projects: ${found.map((p) => p.name).join(', ')}.`,
      rows: found.map((p) => p._id),
    }
  },
  // Works on the plan, not on a new search: a project that matches later is not touched.
  handler: async (ctx, _args, plan) => {
    for (const id of plan.rows) await ctx.db.patch(id, { status: 'archived' })
    return plan.rows.length
  },
})
```

- `plan` runs when the agent asks, before the request is stored. It reads
  only, with the call's row rules. It cannot paginate (read a fixed list with
  `take`), and its input is frozen.
- Without `rows`, the work changes the rows the input names. Without `plan`,
  the person reads the action and the input as JSON.
- Put any other value the work needs into the plan too, such as a price the
  person sees. The handler gets the plan exactly as it was stored.
- A row the plan lists or the input names that the agent may not read fails
  the call with `NOT_FOUND`, so it never reaches a person. Fail in `plan` for
  work that can never run.
- `plan` also runs, right before the handler, when a person calls the
  operation in the app, so the handler always has a plan.

### Approving

`approve` runs the operation as the agent, in the same transaction, on the
stored plan. It does not need the agent or its chat: the person may approve
after the agent has gone.

- It checks the agent's grant again. A revoked connection cannot run.
- It fails with `STALE` when a row the plan lists or the input names changed
  or went away. Nothing is done. The same call is asked again at once, with
  a summary of the data as it is now, and waits for a person as a new request.
- The work, and every internal operation or follow-up it starts, may change
  only the plan's rows and rows it creates itself. Another write fails with
  `FORBIDDEN`, and nothing the work did is kept.
- Other failures are stored on the request with their code.

`approve` returns `{ status: 'approved' }`, or
`{ status: 'failed', error: { code, message } }` when nothing was done. After
`STALE` it also returns `next`, the ID of the new request, so your approval
page can open it. `decline` returns `null`.

The agent learns the outcome with the built-in `check_approval` tool, or by
calling the same tool again with the same `request_id`. A request that nobody
decides expires after 30 minutes.

### Who may decide

The person the agent acts for may always decide. With
`approvers: { 'orders.cancel': ['owner'] }`, an owner of the request's tenant
may decide too. The request's tenant is the call's: the deepest tenant its
input names.

A row that two tenants share can give the other tenant a say too, when the
action asks for it with `sharedRows`:

```ts
approvers: { 'orders.cancel': { roles: ['owner'], sharedRows: true } },
```

A buyer's agent cancels an order. The order names the buyer and the seller
organization, so an owner of the seller may decide too. Only rows that the
call's input names and that the agent may change count. Rows that the call
only reads, such as a seller's public listing in a purchase, give their
tenant no say, and neither does the row of the call's own tenant. When one
such row does not belong to the other tenant, its approvers cannot decide.

Without `sharedRows`, only roles in the call's own tenant count. Keep it that
way unless the other party must agree: an approver of the other tenant may
gain from what the agent asks for.

- `api.agents.pending({})` lists the requests of the signed-in person's own
  agents. With `{ tenantId }`, it adds the requests of that tenant, and of rows
  it shares, that this person may decide as an approver.
- `api.agents.get` returns `null`, and `approve` and `decline` fail with
  `APPROVAL_NOT_FOUND`, for a person who may not decide.
- A role in a tenant that the rows do not name does not count.

::warning
**Known limit:** a parent tenant cannot list the pending requests of the
tenants below it. A request belongs to the deepest tenant that its call names
(a client, not the agency above it). To show the requests of the clients of an
agency, call `pending({ tenantId })` for each client.
::

## The activity feed

Every agent write, approval decision and job run adds one row to `activity`.

- `api.agents.activity({ tenantId })` lists a tenant's activity. Every member
  of the tenant may read it; anyone else gets `NOT_FOUND`.
- `api.agents.activity({})` lists what the signed-in person's own agents did.
  A call without a tenant of its own (`crossTenant`, or only rows of `anyOf`
  tables) is only here, in no tenant's feed.

Each row has the actor (person, agent, or system job), the action, the tool,
the status, and who decided an approval. `limit` is 1 to 200, 50 by default.
Activity and requests are deleted after 90 days by `housekeeping`; see
[The MCP door](/docs/build/agents/mcp-door#run-the-housekeeping).

## What a tool returns

The MCP door sends each result as the tool's `structuredContent`, and as JSON
text for models that read only text. A tool function that a test calls
directly returns the same object; it throws instead of returning `error`.

| Call                                   | Result                                                           |
| -------------------------------------- | ---------------------------------------------------------------- |
| A query, or a write that runs          | `{ status: 'done', result }`                                     |
| A query with `paginationOpts`          | `{ status: 'done', result: { items, next } }`                    |
| A write that waits for a person        | `{ status: 'needs_approval', approvalId, summary, url }`         |
| `check_approval` with `{ approvalId }` | `{ status: 'done', result: { status, summary, result, error } }` |
| A failure                              | `{ error: { code, message } }`, with `isError: true`             |

- `result` is what the operation returns. A retry with the same `request_id`
  returns the stored result; one larger than 64 KiB comes back as
  `{ truncated: true, bytes }`.
- `next` is the `cursor` for the next page, or `null` on the last page.
- For `needs_approval`, the text tells the model to send the person to `url`
  and then to call `check_approval` with `approvalId`.
- In `check_approval`, `status` is `pending`, `approved`, `declined`, `failed`,
  `expired` or `cancelled` (the host was disconnected). `result` is the
  operation's result after approval, and `error` is `{ code, message }` after a
  failure. Both are `null` otherwise. Only the connection that asked can check
  a request.

Known failures keep their code and message: everything from
`fail(code, message)` and the library's own checks. Every other error becomes
`FAILED` with a generic message, and the detail goes to the Convex log. The
[error code reference](/docs/reference/operation-error-codes) lists every
code.
