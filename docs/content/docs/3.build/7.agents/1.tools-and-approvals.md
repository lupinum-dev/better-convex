`@lupinum/better-convex-agents` turns operations from
`@lupinum/better-convex-functions` into tools. A tool call runs the same
operation as the web, with the same policy and row rules, as an **agent**: the
AI host or in-app assistant that acts for one person, within the scopes that
person granted. Start with [Start here](/docs/build/functions/start-here) if
you have no operations yet.

## Give an operation a tool

Add a `tool` field to a query or mutation, as `list` and `archive` in
[Start here](/docs/build/functions/start-here) do:
`tool: { name, description, args }`.

| Field         | Rule                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------ |
| `name`        | 1 to 64 letters, digits, `_` or `-`. Unique. `check_approval` and `housekeeping` are taken |
| `description` | What the tool does, for the model. Say which other tool gives the IDs it needs             |
| `args`        | Optional text for each argument. Convex validators carry no descriptions                   |

The tool's input schema comes from the operation's validators. The tool
checks every input against the same validators, and a wrong field fails with
`INVALID_INPUT` and a message that names it.

- A query with `paginationOpts` becomes a tool with `cursor` and `limit`
  (1 to 100, 50 by default). It returns `{ items, next }`.
- A mutation gets an optional `request_id`. A host that retries with the same
  value gets the first result back; the write runs once. Do not name an
  argument `request_id`, `cursor` or `limit` yourself.

::warning
Change a tool only by adding to it: a new argument is optional, and an old one
keeps its meaning. Hosts keep the tool list until they reconnect. For a
breaking change, add a tool with a new name and keep the old one until no host
uses it.
::

## Collect the tools

One module calls `defineTools` with the operation modules, and exports one
internal function per tool under the tool's name. Logs and usage then name the
tool.

```ts [convex/agents.ts]
import { defineTools } from '@lupinum/better-convex-agents'

import { internal } from './_generated/api'
import { fns } from './functions'
import * as pages from './pages'
import * as projects from './projects'

export const tools = defineTools(fns, { pages, projects }, { functions: internal.agents })

export const { edit_page, list_projects, archive_project, check_approval, housekeeping } =
  tools.functions

// For the approval page: open requests, one request, and the decision.
export const { pending, get, approve, decline } = tools.approvals
// What agents did, newest first.
export const { activity } = tools
```

`functions` must be `internal.<this module>`. When `createMcpServer` loads, a
tool that is not exported fails, with the missing names in the message. An
operation in a module that you do not pass to `defineTools` has no tool.

## Hold an action for a person

Set the agent rule of the action to `'approve'` in the
[policy](/docs/build/functions/policy-and-roles). An agent that calls the tool
then gets this result instead of the effect:

```json
{
  "status": "needs_approval",
  "approvalId": "k57…",
  "summary": "Archive the project \"Website relaunch\".",
  "url": "https://app.example.com/approvals/k57…"
}
```

The agent tells the person to open the link. Your approval page at
`/approvals/[id]` reads the request with `api.agents.get` and calls
`api.agents.approve` or `api.agents.decline`. `starters/mcp-oauth-agent` has
the page in `app/pages/approvals/[id].vue`. Set `SITE_URL` on the Convex
deployment: the link is built from it.

Use `'approve'` for every action that destroys, publishes, sends, spends or
changes who has access. See [Prompt injection](/docs/build/functions/threat-model#prompt-injection).

### The summary

Give the mutation an `approval` function, as `archive` in Start here does. It
returns the one sentence the person reads.
It runs before the request is stored, with the call's row rules. Every row it
reads, and every row the input names, is fingerprinted. Fail in it for work
that can never run, so it never reaches a person. Without `approval`, the
person sees the action and the input as JSON.

### Approving

`approve` runs the operation as the agent, in the same transaction:

- It checks the agent's grant again. A revoked connection cannot run.
- It fails with `STALE` when a row the person based the decision on changed
  since the request. Nothing is done; the agent can ask again.
- Other failures are stored on the request with their code.

The agent learns the outcome with the built-in `check_approval` tool, or by
calling the same tool again with the same `request_id`. A request that nobody
decides expires after 30 minutes.

### Who may decide

The person the agent acts for may always decide. With
`approvers: { 'orders.cancel': ['owner'] }`, an owner of the request's tenant
may decide too. The request's tenant is the call's: the deepest tenant its
input names.

A row that two tenants share gives both of them a say. When every row that the
request touches names another tenant in one of its fields, the approvers of
that tenant may decide too. A buyer's agent cancels an order: the order names
the buyer and the seller organization, so an owner of the seller may decide.
The rows that the request touches are the rows its input names and the rows
its `approval` function reads; the row of the call's own tenant does not count.
When one row does not name the tenant, its approvers cannot decide.

- `api.agents.pending({})` lists the requests of the signed-in person's own
  agents. With `{ tenantId }`, it adds the requests of that tenant, and of rows
  it shares, that this person may decide as an approver.
- `api.agents.get` returns `null`, and `approve` and `decline` fail with
  `APPROVAL_NOT_FOUND`, for a person who may not decide.
- A role in a tenant that the rows do not name does not count.

::warning
**Known limit:** a parent tenant cannot list the pending requests of the
tenants below it. A request belongs to the deepest tenant that its call names
(a client, not the agency above it). To show the requests of the clients of an
agency, call `pending({ tenantId })` for each client.
::

## The activity feed

Every agent write, approval decision and job run adds one row to `activity`.

- `api.agents.activity({ tenantId })` lists a tenant's activity. Every member
  of the tenant may read it; anyone else gets `NOT_FOUND`.
- `api.agents.activity({})` lists what the signed-in person's own agents did.

Each row has the actor (person, agent, or system job), the action, the tool,
the status, and who decided an approval. `limit` is 1 to 200, 50 by default.
Activity and requests are deleted after 90 days by `housekeeping`; see
[The MCP door](/docs/build/agents/mcp-door#run-the-housekeeping).

## Errors that agents see

A tool that fails returns `{ error: { code, message } }`. Known failures keep
their code and message: everything from `fail(code, message)` and the
library's own checks. Every other error becomes `FAILED` with a generic
message, and the detail goes to the Convex log. The
[error code reference](/docs/reference/operation-error-codes) lists every
code.
