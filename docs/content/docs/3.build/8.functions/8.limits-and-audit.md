Both are written in the policy, next to the roles. There is no second place to
configure them.

```ts [convex/policy.ts]
export const policy = definePolicy({
  actions: [
    'invites.send',
    'reports.generate',
    'contact.send',
    'projects.archive',
    'members.remove',
  ],
  roles: { owner: ['*'] },
  scopes: {},
  public: ['contact.send'],
  limits: {
    'invites.send': { max: 10, every: 'minute' },
    'reports.generate': { max: 30, every: 'hour', per: 'tenant' },
    'contact.send': { max: 60, every: 'minute', per: 'everyone' },
  },
  audit: ['projects.archive', 'members.*'],
})
```

## Rate limits

`max` is how many calls the bucket holds. It refills `max` per `every`
(`'second'`, `'minute'`, `'hour'` or `'day'`), continuously: ten calls a minute
gives back one call every six seconds. `max` is a whole number of at least 1.

`per` says whose calls share a bucket:

| `per`              | Bucket                                                               |
| ------------------ | -------------------------------------------------------------------- |
| `'user'` (default) | The person. For an agent: the person and the client or in-app agent. |
| `'tenant'`         | The call's tenant. A call without a tenant counts per user.          |
| `'everyone'`       | One bucket for the whole action.                                     |

A visitor who is not signed in has no user, so a public action uses the
`everyone` bucket whatever `per` says. `everyone` is one document that every
call writes: use it for low-volume public actions such as a contact form, not
for busy ones.

A call over the limit fails with `RATE_LIMITED` and the message
`Too many requests. Try again in N seconds.`

What counts:

- The policy decides first. A call it denies (`NOT_SIGNED_IN`, `FORBIDDEN`,
  `NOT_FOUND`) never takes a token.
- The token is taken in the transaction of the call, before the handler. A
  call that fails gives its token back, so a call that fails does not count.
- Every mutation built with `fns` is limited, public or internal. An internal
  mutation that is scheduled, or run from an action, takes its own token.
- A mutation that another mutation runs with `ctx.runMutation` takes no second
  token for an action the outer call already took one for. The outer call
  passes that on.
- Jobs and other system calls are never limited.
- An agent's call is limited like a person's. A request that waits for
  approval takes no token. When the person approves it, the run takes none
  either: the person is the gate. The agent's request still counts against its
  60 writes a minute.
- Wrong definitions throw when the policy is defined: an action that is not in
  `actions`, `max` below 1 or not whole, an unknown `every` or `per`.

### Actions

Limits apply to mutations only. A Convex action has no database of its own,
so it cannot take a token. Limit the action of the internal mutation it runs
with `ctx.run`: that mutation takes the token, whoever calls it. A
`limits` entry for an action that no mutation uses (a query only) throws when
the query is defined: "is limited, but no mutation uses it".

### Storage

Buckets live in the library table `rateLimits`: one small document per limited
key. Their number is bounded by users times limited actions, plus the tenants
and actions with `per: 'tenant'`. If you use agents, `housekeeping` deletes
buckets idle for more than a day. Without agents nothing deletes them; a full
bucket costs one row.

## Audit log

The log follows the action, whichever door the call came in by. After an
audited mutation succeeds, the library writes one row to the `auditLog` table,
in the same transaction. Every audited operation writes its own row: a public
mutation, an agent's tool call (also when a person approved it), or an internal
mutation that was scheduled or run for a person or an agent. One exception: an
operation that another audited mutation runs with `ctx.runMutation` writes no
row of its own. Its ids join the outer call's row. If the outer call is not
audited, the inner call writes its own row, with its own action.

| Field      | Content                                                                                               |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| `actor`    | Who: the same record as in `activity`. For an agent: door `mcp` or `app`, with `clientId` or `agent`. |
| `action`   | The policy action of the outer call.                                                                  |
| `tenantId` | The call's tenant, when it has one.                                                                   |
| `rows`     | The ids the call inserted, patched, replaced or deleted, at most 50.                                  |
| `more`     | How many ids there were beyond the 50.                                                                |

The time is the row's `_creationTime`. The log holds no values, no arguments
and no results: only ids. A call that fails writes nothing, because the whole
transaction rolls back. System actors (jobs) and signed-out visitors have no
row. `activity` stays as it is: it is the agents' replay and history, not the
audit log.

`audit` takes the same patterns as `roles`: `'projects.archive'`,
`'members.*'` or `'*'`. A pattern that matches no action throws when the policy
is defined.

### Reading the log

The library does not decide who may read it. Write an operation with its own
action and call `auditTrail`:

```ts
import { auditTrail } from '@lupinum/better-convex-functions'

export const trail = query({
  action: 'audit.read',
  args: { orgId: v.id('orgs'), paginationOpts: paginationOptsValidator },
  returns: v.any(),
  handler: (ctx, { orgId, paginationOpts }) => auditTrail(ctx, { tenantId: orgId, paginationOpts }),
})
```

It returns one page of the tenant's rows, newest first. No retention is
applied: the log is meant to last. When a person deletes their account,
[erasure](/docs/build/authentication/account-deletion) removes their id from
the rows and keeps the rows themselves.
