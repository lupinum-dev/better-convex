title: Transactional auth email
description: Bind reset, verification, and email-code callbacks to the current Convex invocation.

Use a request-bound option factory when an auth callback must submit work to
Convex. `emailAndPassword`, `emailVerification`, and `emailOTP` accept their
existing options or a synchronous or asynchronous factory receiving `ctx`.
Static options remain supported.

The application owns recipients, templates, delivery and retries. Better
Convex does not install a sending provider or render emails.

## Submit durable work

Await the application's durable submission inside the callback. Do not await a
mail provider's network response or start an untracked promise. Auth token
creation and a later submission can be separate transactions; test submission
failure and safe user retries in the application.

The pinned Better Auth runtime awaits background-capable callbacks when no
background handler is configured, but can catch and log their errors. A normal
auth HTTP response is not proof that email submission succeeded. Preserve a
non-enumerating user response and provide safe operational visibility for
submission failures. Never include the credential-bearing payload in an error.

```ts [convex/auth.ts]
import {
  createBetterConvexAuth,
  requireWritableAuthCtx,
} from '@lupinum/better-convex-nuxt/better-auth/server'

import { components, internal } from './_generated/api'
import type { DataModel } from './_generated/dataModel'

export const auth = createBetterConvexAuth<DataModel>(components.betterAuth, {
  emailAndPassword: (ctx) => ({
    revokeSessionsOnPasswordReset: true,
    async sendResetPassword({ user, url }) {
      requireWritableAuthCtx(ctx)
      await ctx.runMutation(internal.authMail.submitReset, {
        recipient: user.email,
        resetUrl: url,
      })
    },
  }),
})
```

`internal.authMail.submitReset` is an application-owned internal mutation in
this example, not a library export. It must durably enqueue or schedule the
approved message, with bounded retry and secret-retention rules. Do not expose
a public endpoint accepting arbitrary recipients or reset URLs.

## Keep construction read-only

Auth construction also runs in queries. A factory must only construct options
and callbacks; it must not send mail. Call `requireWritableAuthCtx` inside the
callback that writes, not at the top of the factory. It narrows the context to
a mutation or action and rejects read-only execution.

Each factory runs for its own auth invocation. Keep request state in its
closure, not a module-level variable. Do not cache options that close over a
request context.

## Preserve provider behavior

Return the same upstream option shape used for static configuration. Callbacks
retain their upstream arguments and return behavior. Password hashing,
minimum length, automatic sign-in and other owned settings remain protected;
the password-option allowlist also applies to factory results.

Factories may return `false` for password or email-OTP disablement. Verification
factories must return an options object. A thrown factory error or malformed
result fails auth construction with `AUTH_CONFIG_INVALID`; private details are
not included. Sending callback failures remain part of the upstream request
flow and must not contain secrets in their diagnostics.

Use environment-independent build options for schema generation. A
request-bound factory is not a schema-discovery mechanism. Every enabled
plugin must match the generated local component schema.

Email codes need their own expiry, abuse limits and delivery-latency tests. A
durable queue does not automatically stop sending after a code expires. Never
log codes, reset URLs or queued message bodies in application diagnostics.
