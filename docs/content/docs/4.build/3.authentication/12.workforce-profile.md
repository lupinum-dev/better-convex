---
title: Workforce authentication candidate
description: Configure the fixed password and TOTP candidate with one canonical auth component.
---

The workforce candidate requires a verified email address, a password, and a
time-based one-time password (TOTP) before a session can access business functions.
Better Auth owns the credentials and ceremonies. The Convex component checks the
persisted proof before it admits a session.

This candidate is not yet a complete production workforce baseline. Invitation
recovery and complete reference-application and hosted verification remain release
gates. Replay and session management have local HTTP and open-subscription expiry
proofs. These checks are not a production certification.

## Generate one workforce component

Use a fresh local component. Do not apply this schema to an existing populated
auth component without an explicit migration plan.

Use the package-owned build options:

```ts [convex/betterAuth/schema-options.ts]
import { createWorkforceAuthSchemaOptions } from '@lupinum/better-convex-nuxt/better-auth/server'

export default createWorkforceAuthSchemaOptions()
```

Generate the schema and metadata together:

```bash
pnpm exec better-convex auth schema \
  --config convex/betterAuth/schema-options.ts \
  --output convex/betterAuth
```

The builder needs no runtime secrets or email callbacks. It includes the factor,
session-proof, signing-key, and database rate-limit fields. Use these options
only for schema generation, never as a runtime auth configuration.

Export all adapter functions from the local component, including `assertProfile`,
`sessionAdmission`, and the five workforce session functions. Use the generated
adapter template and regenerate Convex bindings. Mount only that component as
`betterAuth`; do not also mount the packaged ordinary-auth component.

## Select the fixed runtime profile

The following configuration disables public signup. An application that enables
signup must supply its own `beforeUserCreate` admission callback.

```ts [convex/auth.ts]
import { createBetterConvexAuth } from '@lupinum/better-convex-nuxt/better-auth/server'
import { components } from './_generated/api'
import type { DataModel } from './_generated/dataModel'

export const auth = createBetterConvexAuth<DataModel>(components.betterAuth, {
  workforce: true,
  emailAndPassword: { disableSignUp: true },
})
```

Configure request-bound verification and reset callbacks before enabling those
email flows. Follow [transactional email](/docs/build/authentication/transactional-email). This example
does not provision users or deliver email.

The factory rejects a runtime/component profile mismatch. It does not infer or
change the component's policy from a request. The component assertion returns no
auth rows and remains internal to the backend.

The profile fixes these settings:

- verified email before password login;
- no automatic session after signup;
- no trusted-device bypass or session cookie cache;
- no automatic session refresh;
- a 60-minute idle session limit;
- a 12-hour absolute session limit;
- fresh full authentication within five minutes for reviewed sensitive changes;
- reset-driven invalidation of existing sessions.

Do not pass `twoFactor` options with `workforce: true`. The profile owns them.
Email OTP, social login, organizations, and delegated OAuth cannot be combined
with this candidate. These features need separate reviewed profiles; silently
adding another login route can bypass a fixed authentication policy.

## Respect restricted sessions

Password-only, factor-enrollment, and recovery-code sessions are restricted.
They cannot obtain a Convex session token or pass the component's business-user
helpers. Confirming enrollment does not itself grant business access. Complete
a fresh password-and-TOTP login afterward.

Use the integrated `useConvexAuth().client` for each ceremony. Its promise waits
for the canonical provider session and the matching Convex runtime to settle.
A valid restricted session settles as anonymous to Convex, while the provider
cookie remains available to guarded setup endpoints. The operation can therefore
return an authenticator setup URI or recovery codes without granting business
access. Keep those values in temporary component memory, never logs or storage.
Unexpected refusals and transport failures still reject reconciliation.

Wait for a new authenticator code after confirming enrollment. The component
rejects reuse of the accepted code across separate login challenges. The same
rule applies when two challenges finish concurrently.

Recovery consumes the code and invalidates earlier full sessions. A recovery
session can enter the reviewed factor-replacement ceremony, but it is not a
second route into business data. Existing factor material remains active until
the replacement proof succeeds.

Most account-management routes currently fail closed. Do not bypass them with
direct adapter calls from public application functions. In particular, do not
expose raw session lists, component rows, or backup-code export methods.

## Manage sessions through owned helpers

Use `authComponent.workforceSessions` in protected application functions:

- `list(ctx, { cursor, numItems })` returns at most 50 session summaries per page.
- `touch(ctx)` extends idle time after foreground user activity.
- `revoke(ctx, sessionId)` removes one session owned by the current user.
- `revokeAll(ctx)` invalidates all current sessions and pending login challenges.

The helpers derive the actor from the verified Convex session identity. Do not
accept an actor user ID or session ID from a browser. The component checks current
full authentication again in each operation. These authority-removing operations
do not require authentication within the previous five minutes.

Return only the sanitized session list. It includes a session ID, current-session
flag, authentication time, start time, expiry, and assurance method. It contains
no session token, IP address, or user agent.

Call `touch` only after a user interaction. Do not call it from polling, SSR,
token renewal, or a periodic heartbeat. Touch preserves the original 12-hour
limit and authentication time. It cannot revive an expired or revoked session.
The backend cannot prove that a human caused a touch. A stolen session token can
extend its idle deadline until the unchanged absolute limit.

Each new session schedules one expiry chain using its physical database ID.
Touch does not schedule another job. At the old deadline, the job either deletes
the expired session or schedules its next deadline. Generic adapter writes cannot
shorten a session deadline or extend it. Use the owned revoke or touch operation.
New operations reject expired sessions at the deadline. Existing subscriptions
also depend on scheduler execution; do not promise a zero-latency cutoff.

The local runtime proof uses a real password-and-TOTP session and an internal,
disposable-fixture deadline accelerator. It observes an uninterrupted connection
lose admission after the production expiry callback deletes that session. A
second valid session remains admitted. This does not measure hosted scheduler
latency or change the production idle-time policy.

`get-session` remains available to live restricted setup sessions. It does not
return usable authority for a stale generation or expired session. Sign-out
remains available without full authentication.

## Preserve one-time authenticator use

The provider remains responsible for credential verification. An additional
package-owned check uses the same pinned OTP utility to record matching time
counters. The canonical mutation requires a current matching counter and an
unchanged factor fingerprint before it creates a full session or promotes a
pending factor.

The component records a one-way, factor-keyed replay marker in its existing
verification table. It does not store the submitted code or plaintext factor
secret in the marker or operation metadata. Re-encrypting an unchanged factor
does not reset its replay identity. Generation changes and new challenges do
not reset it either.

Marker insertion and admission share one transaction. Failure rolls both back.
A lost response after a successful commit does not make the code reusable.
Markers last at least two minutes and cover every recorded matching counter.
A naturally repeated six-digit value can be rejected conservatively while its
marker remains live. Wait for a different code and retry.

Generic adapter writes cannot forge, rename, or remove live replay markers.
Expiry cleanup uses canonical database time and processes at most 128 rows per
call. This keeps a large expired backlog from blocking verification lookup.
Provider/database clock skew can cause a false rejection, not an extended
acceptance window. Finite retention does not cover arbitrary backward clock
jumps in the database runtime.

## Keep application authorization separate

Use component user helpers for live session admission. Check current membership,
suspension, role, and resource ownership in each protected Convex operation.
For a write, perform the authorization check in the same transaction.

An email allowlist in `beforeUserCreate` is not a complete invitation system.
It does not prove possession of an invitation, prevent account pre-creation, or
decide how a previously registered account joins an organization. Keep those
application decisions explicit and test them before onboarding real users.
