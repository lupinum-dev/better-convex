These APIs are auto-imported in Nuxt application code. Import generated function references from `#convex/api`. Plain Vue applications import the same composables from `@lupinum/better-convex-vue`.

The composables return objects of refs and functions. Destructure them in `<script setup>` so that templates unwrap the refs. The functions do not depend on `this`, so destructuring is safe.

## Query APIs

### `useConvexQuery`

```ts
const { data, status, pending, error, isStale, blockedBy, execute, refresh } = useConvexQuery(
  query,
  args,
  options?,
)
const settled = await useConvexQuery(query, args, options?) // optional initial-settlement barrier
```

Exactly empty query validators may omit `args`. A validator with any declared key requires that position, even when every key is optional. Use `'skip'` as the argument value to make the state idle.

Nuxt options: `auth`, `keepPreviousData`, `immediate`, `lazy`, `server`. Plain
Vue omits `lazy` and `server`.

Immediate readonly state: `data`, `status`, `pending`, `error`, `isStale`,
`blockedBy`, `execute`, `refresh`. The return type is `UseConvexQueryState<Data>`.

`data` and `error` use `undefined` for absence. A query result of `null` is successful data. `error.functionName` names the failed query.

`blockedBy` tells why the query is not running. It is `'skip'` for skipped arguments, `'manual'` for an `immediate: false` query that was not started, `'auth'` while the query waits for auth, needs a signed-in user, or has an auth error, and `null` when the query may run. The type is `ConvexQueryBlockedBy`.

The Nuxt return is also a native Promise; its awaited result is a separate non-Promise view of the same refs. Initial success, error, skip, and `server: false` resolve. [Query guide](/docs/build/queries/queries).

### `useConvexPaginatedQuery`

```ts
const {
  data,
  status,
  pending,
  error,
  isStale,
  blockedBy,
  canLoadMore,
  isLoadingMore,
  isExhausted,
  loadMore,
  execute,
  refresh,
  reset,
} = useConvexPaginatedQuery(query, args, {
  initialNumItems,
  initialCursor?,
  auth?,
  keepPreviousData?,
  immediate?,
  lazy?,
  server?,
})
```

`initialNumItems` is required. Plain Vue omits `lazy` and `server`. The return type is `UseConvexPaginatedQueryState<Item>`.

- `data` is the flattened readonly item array, or `undefined` before the first page exists.
- `status` and `pending` describe the first page only. Status is `idle`, `pending`, `success`, or `error`. Loading or failing a later page leaves `status` at `success`.
- `error` is the first-page error, else the error of a failed later page. A failed later page keeps the items loaded before it.
- `canLoadMore` is `true` when the first page succeeded, the last loaded page is not the end, and no later page is loading.
- `isLoadingMore` is `true` while a later page loads. `isExhausted` is `true` when the last loaded page is the end of the list.
- `loadMore(numItems)` returns `Promise<void>`. The Promise resolves when the page loads, fails, is replaced, or the list resets or is disposed. It never rejects. Without `canLoadMore`, the call does nothing and resolves immediately. After a later page fails, `loadMore()` retries it.
- `blockedBy` has the same meaning as for `useConvexQuery`.

The Nuxt return follows the same native Promise/state settlement contract as a regular query. The server renders only the first page. [Pagination guide](/docs/build/queries/pagination).

## Write APIs

### `useConvexMutation`

```ts
const { mutate, data, status, pending, error, reset } = useConvexMutation(mutation, {
  optimisticUpdate?,
})
```

`mutate(args)` resolves with the mutation result and rejects with a `ConvexCallError` that carries `functionName`. `data`, `status`, `pending`, and `error` are readonly refs that describe the newest call. `reset()` returns the state to `idle` and clears `data` and `error`; a call that is still in flight settles its own Promise but no longer changes the state. The return type is `UseConvexMutationReturn<Mutation>`.

`optimisticUpdate(store, args)` is synchronous and uses Convex's `OptimisticLocalStore` methods `getQuery`, `getAllQueries`, and `setQuery` directly. [Mutation guide](/docs/build/write-data/mutations).

### `useConvexAction`

```ts
const { run, data, status, pending, error, reset } = useConvexAction(action)
```

`run(args)` resolves with the action result and rejects with a `ConvexCallError` that carries `functionName`. The state and `reset()` behave as for `useConvexMutation`. The return type is `UseConvexActionReturn<Action>`. [Action guide](/docs/build/write-data/actions).

### Call failures raised by the library

| Code                 | When                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| `IDENTITY_CHANGED`   | The signed-in identity changed before the call settled               |
| `CANCELLED`          | The call started after its component or effect scope was disposed    |
| `CLIENT_UNAVAILABLE` | No browser Convex client exists, for example during server rendering |

Application errors thrown with `ConvexError` keep their own `data.code`. See [error types](/docs/reference/error-types).

### `useConvexForm`

```ts
const { submit, data, status, pending, error, issues, fieldErrors, formError, reset } =
  useConvexForm(mutation, { schema, toArgs?, mapError? })

const result = await submit(values, contextualArgs?)
```

Validates external values with Standard Schema, transforms them into arguments for one mutation, and submits them. The composable never owns values, touched/dirty state, navigation, or toasts. The return type is `UseConvexFormReturn`.

- `submit()` resolves with `{ ok: true, data }` or `{ ok: false, error }` for validation and mutation failures.
- A second `submit()` while one is pending rejects with a `ConvexCallError` with code `SUBMIT_IN_PROGRESS` and sends no mutation. Disable the submit control while `pending` is `true`.
- `reset()` returns to `idle`, clears `data` and `error`, and lets a new submission start at once. A pending submission still settles its own Promise but no longer changes the state.

[Form submission guide](/docs/build/write-data/forms).

## Authentication API

### `useConvexAuth`

```ts
const { status, pending, user, error, client, ready } = useConvexAuth()
```

Returns the canonical authentication state and one configured, integrated Better Auth client:

- `status`: `loading`, `anonymous`, `authenticated`, or `error` for the currently usable identity;
- `pending`: Better Auth session or operation work, independent from `status`;
- readonly `user` and `error` refs; `user` is a `ConvexUser` or `null`;
- `client`: the inferred Better Auth client. It is never `null`;
- `ready()`: waits for initial Convex identity settlement.

The real `client` exists only in the browser after the Convex runtime starts. During server rendering and before that point, `client` is an inert stand-in. You can destructure it and read its properties. Calling any of its methods throws a `ConvexCallError` with code `CLIENT_UNAVAILABLE`. Call `client` methods from browser event handlers or `onMounted()`.

Render auth states explicitly so application layout and accessibility stay product-owned:

```vue
<script setup lang="ts">
const { status, error } = useConvexAuth()
</script>

<template>
  <AccountSkeleton v-if="status === 'loading'" />
  <AccountMenu v-else-if="status === 'authenticated'" />
  <SignInCard v-else-if="status === 'anonymous'" />
  <ErrorCard v-else :message="error?.message ?? 'Authentication failed'" />
</template>
```

Synchronous Better Auth methods such as `client.useSession()` remain synchronous. Every
Promise-returning client operation re-reads the canonical provider session and settles only after
Convex accepts that exact session generation. `$fetch`, `$store`, `hydrateSession`, and the
module-owned Convex token action are not exposed.

[Auth state guide](/docs/build/authentication/auth-state-and-user).

Query product profiles directly with `useConvexQuery(..., { auth: 'required' })`; session identity remains owned by `useConvexAuth()`.

## Client and configuration

### `useConvex`

```ts
const convex = useConvex()
```

Returns one stable handle containing exactly `query`, `mutation`, `action`, and `onUpdate`. The return type is `ConvexClientHandle`.

The handle behaves like the raw Convex client: in the browser, its calls reject with the error Convex raised, such as a plain `ConvexError` or `Error`, not a `ConvexCallError`. Only an identity change during a call rejects with a `ConvexCallError` coded `IDENTITY_CHANGED`. Pass a caught error through `normalizeConvexError(error, { functionName })` before you read `kind` or `code`, or use `useConvexMutation` and `useConvexAction`, which do that for you:

```ts
try {
  await convex.mutation(api.notes.create, { title })
} catch (error) {
  const failure = normalizeConvexError(error, { functionName: 'notes:create' })
  if (isConvexCallError(failure, 'NOTE_LOCKED')) showLockedNotice()
}
```

In Nuxt, calling `useConvex()` is safe everywhere. During server rendering, or when no Convex URL is configured, `query`, `mutation`, and `action` reject and `onUpdate` throws a `ConvexCallError` with code `CLIENT_UNAVAILABLE`. Use `useConvexQuery` for server-rendered data and `serverConvex(event)` in Nitro handlers. Plain Vue throws when the `createBetterConvex()` plugin is not installed.

### `useConvexAttachment`

```ts
useConvexAttachment()
```

Client-only. Returns the frozen `@lupinum/better-convex-vue/embedded` attachment owned by the current Nuxt app for an explicitly embedded Vue application. It contains no credentials or Better Auth controls. On the server, or when no Convex URL is configured, it throws a `ConvexCallError` with code `CLIENT_UNAVAILABLE`.

### `useConvexConfig`

```ts
const { url, siteUrl } = useConvexConfig()
```

Returns exactly the readonly resolved Convex deployment URL and HTTP Actions site URL. It exposes no auth, query policy, upload policy, logging, client, server, or server-secret fields.

### `useConvexConnectionState`

```ts
const { state, isConnected, isReconnecting, pendingMutations, pendingActions } =
  useConvexConnectionState()
```

Returns `UseConvexConnectionStateReturn`. Every field is a computed ref. During server rendering, and in a Nuxt build without a Convex URL, it reports the disconnected state that the browser runtime starts from. Use operation and query state for product-level availability. [Connection state guide](/docs/build/application-behavior/connection-state).

## File API

### `useConvexFileUpload`

```ts
const { upload, data, status, pending, error, progress, cancel, reset } = useConvexFileUpload(
  generateUploadUrlMutation,
  { maxSize?, allowedTypes? },
)
```

`upload(file, args?)` resolves with the branded storage ID. Generated mutation arguments keep their Convex arity: required arguments are required by `upload(file, args)`. `progress` exposes `loaded`, `total`, and `percent`. The return type is `UseConvexFileUploadReturn<Mutation>`.

- `cancel()` stops the upload in flight, if any. That upload rejects with `CANCELLED` and the state returns to `idle`. When no upload is in flight, `cancel()` does nothing.
- `reset()` stops any upload in flight in the same way and clears `data`, `error`, and `progress`.
- Unmounting the owning component stops the upload in flight with `CANCELLED`.

`upload()` rejects with a `ConvexCallError`:

| Code                    | When                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| `FILE_TOO_LARGE`        | The file is larger than `maxSize`; no request is sent                |
| `FILE_TYPE_NOT_ALLOWED` | The MIME type does not match `allowedTypes`; no request is sent      |
| `UPLOAD_IN_PROGRESS`    | Another upload of the same composable is pending                     |
| `CANCELLED`             | `cancel()`, `reset()`, or scope disposal stopped the upload          |
| `IDENTITY_CHANGED`      | The signed-in identity changed during the upload                     |
| `CLIENT_UNAVAILABLE`    | No browser Convex client exists, for example during server rendering |

Other failures are the normalized upload-URL mutation or transport error. Every error carries the upload-URL mutation in `functionName`. `CANCELLED` and `IDENTITY_CHANGED` return the state to `idle`, not `error`.

Resolve URLs with an ordinary `useConvexQuery` call. Products that accept several files own their item state, worker count, retry policy, and persistence around this one-file primitive. [File guide](/docs/build/files/upload-files).
